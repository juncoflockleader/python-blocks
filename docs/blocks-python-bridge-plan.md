# Blocks and Python bridge implementation plan

Status: **implemented and verified**, 2026-10-07. The [completion audit](blocks-python-bridge-audit.md) records all B01–B08 evidence. Learners can edit supported expressions, assignments, control flow, functions and existing playground calls, return to usable blocks, and run the same program with its original assets. The completed [2D baseline](2d-parity-audit.md) passes the full regression. Human learner sessions remain future work under the [pilot protocol](python-bridge-learner-pilot.md).

## Representation and ownership

The committed Blockly project remains the editable structured representation. Entering Python creates a draft of the current main source and records the exact project revision from which it came. The draft is its own saved state: syntax errors, unsupported code and unfinished edits survive reload and project download. A draft never silently replaces or executes stale blocks.

**Apply to blocks** parses and converts in isolation, compiles the candidate, checks the supported semantics, then installs one undoable change. Conversion failure leaves both the current blocks and the exact draft intact. **Run Python** performs the same validation and conversion before running the resulting captured program; there is no unrestricted alternate execution mode that bypasses the library, diagnostics or limits. Switching to inspect blocks does not discard a pending draft. Starting a fresh draft from changed blocks or discarding text is an explicit action with a recoverable prior state.

Scene metadata remains outside source: sprites, images, frames, sounds, worlds, touch mappings and watches keep their stable IDs. Pinned module definitions remain immutable; their generated source is inspectable separately from the editable main file. Main-file calls may use existing module bindings. The bridge does not interpret a concatenated preview of several Python files as one program.

Python formatting and comments belong to the draft. Successful conversion may produce differently formatted generated Python, so retain the submitted source and show what was applied. Preserve comments in blocks where they have an unambiguous statement attachment and preserve all other comments in the retained source. Never claim byte-for-byte source round-tripping. Unchanged blocks and symbol references should retain identity and layout; removed active code and inactive drafts must remain recoverable through Undo and the saved source snapshot.

## Supported Python

The first bridge covers the existing representable language and curated library surface, including:

- Exact integer/float/string/Boolean/None literals; arithmetic, comparisons and short-circuit expressions; explicit conversions; lists/dictionaries and their supported operations.
- Project/local/parameter reads and assignments; collection mutation; `if`/`elif`/`else`; `for` iteration/range/repeat patterns; `while`; `break`, `continue`, `pass` and returns.
- Named synchronous and async functions with positional parameters, recursion, current supported function values/lambdas, and calls to existing pinned modules. The existing restrictions on closures and async function values remain explicit.
- Event emission, explicit waits and the generated registration patterns for project, sprite and kind handlers. Handler order, ownership, async requirements and cancellation semantics are preserved.
- Existing pen, sprite, appearance, sensing, input, sound, game and world operations. Literal sprite/asset/world references resolve against the captured project; unknown references produce useful errors.

Syntax outside the block model receives a positioned explanation and stays in the draft. Examples include arbitrary imports/packages, classes, exception handling, decorators, general generators/comprehensions, unrestricted attribute operations, variadic/default/keyword-only function signatures and unsupported closure capture. The one comprehension exception is Blockly's exact generated three-or-more-item text join, which evaluates the complete item list before converting values to strings. Extending support requires a semantic mapping and tests; raw-code blocks are not a fallback.

The converter must not silently rewrite evaluation order, scope, operand-returning Boolean logic, chained comparisons, augmented assignment on aliased objects, handler registration timing or library completion semantics. If an operation needs a new block to retain those semantics, implement it or explain why conversion is unavailable. A generated existing project must have a lossless unchanged path, including legacy block shapes, disabled code and inactive drafts.

## Architecture

1. A dedicated parser worker loads the same pinned local CPython/Pyodide runtime as execution. Parsing never runs learner imports or statements and does not share a running project's interpreter.
2. Python's `ast` and `tokenize` produce a bounded syntax tree, exact literal values, comments and source positions. Convert Python's byte/character columns to JavaScript UTF-16 offsets at this boundary. Syntax and compiler-context errors are returned as data. Source, tree size/depth, startup and parsing time are bounded; cancellation terminates the worker and stale results are ignored.
3. A TypeScript converter resolves names/scopes, known imports, function signatures, handler registrations and library operations into an isolated Blockly workspace. It preserves project metadata and reconciles existing identities where possible. Unsupported nodes return precise diagnostics, never partial workspace mutations.
4. Compile that candidate with the existing compiler. Compare the resulting program structure under narrowly defined normalizations, and exercise behavior in native Python and Pyodide. Reordering arbitrary executable statements or erasing unsupported constructs is not an allowed normalization.
5. A bridge controller owns draft/base revision, conversion lifecycle, conflict checks, history and serialization. Editor controls expose draft validation, apply/run, generated source inspection, recovery and positioned errors. Existing runner, scene lifecycle and export paths consume the accepted compilation.

Python's official [AST documentation](https://docs.python.org/3.14/library/ast.html) distinguishes parsing from compilation checks and defines UTF-8 AST columns; its [tokenizer documentation](https://docs.python.org/3.14/library/tokenize.html) supplies comment tokens and character-based token positions. Parsing and compilation are used only for inspection here. The runtime is pinned locally; the documentation's latest patch version does not change the interpreter bundled by this project.

## Implementation sequence

1. Build and verify B01, including an exact and versioned parser protocol.
2. Implement B02 with isolated conversion and explicit semantic checks.
3. Add B03 scope/identity reconciliation and B04 library coverage against generated fixtures.
4. Add B05 project history/serialization, then B06 editor integration and B07 run/export integration.
5. Exercise real learner edits across every representative project, fix discovered gaps, and complete B08. No row is complete on test counts alone.

The roadmap also calls for a learner pilot to guide the later expansion of written Python. Automated behavioral and usability checks can prepare that pilot; they cannot stand in for human learning evidence. Record the pilot protocol and any actual observations separately, without claiming unperformed user research.

The future AI helper remains BYO API key and assistance-only. This bridge is authored by the learner; it adds no AI authoring or automatic input.

## Core conversion evidence

Verified on 2026-10-07. The [candidate pipeline](../src/bridge/converter.ts), [core mappings](../src/bridge/core-converter.ts) and [semantic comparison](../src/bridge/ast.ts) implement B02. Conversion captures the base project before parsing, constructs blocks in an isolated workspace, validates project limits, compiles and reparses the candidate, and compares syntax trees. It returns a candidate or positioned diagnostics; it never installs changes into the live workspace. The result retains exact submitted text and source-to-block spans. Same-line statement comments also become block comments; broader comment attachment and durable source storage remain integration work.

Supported core mappings cover exact literal values, unary plus/minus, arithmetic, operand-returning Boolean operations, simple comparisons/membership, conversions, scoped project variables, list/dictionary literals and supported mutations/accessors, conditionals, range/iteration/repeat loops, while, break/continue and pass. Language version 19 adds the ordinary `py_unary` block; prior projects through version 18 and pinned modules from versions 5–18 remain readable. Reserved generated repeat counters cannot be read or reassigned by accepted source.

The comparison only ignores locations/comments and literal spelling, removes no-op `pass`, flattens same-operator Boolean grouping, supplies implicit built-in range defaults and normalizes inaccessible repeat-counter names. It does not reorder executable statements or imports. Chained comparisons, augmented/multiple/destructuring assignments, slicing, loop-else, arbitrary imports, unsupported literals and argument forms receive explicit errors. These restrictions prevent duplication of operand evaluation, changes to aliased objects and implicit coercions.

Forty-five [converter tests](../tests/unit/bridge-converter.test.ts) use the actual native parser and Blockly compiler. They compare Python execution for exact values, short-circuiting, arithmetic grouping, mutable aliases and shallow copies, assignment/key/default evaluation order, mixed-type errors, case-sensitive names, read-before-assignment, loop boundaries and random/repeat patterns. They also cover positioned rejection, cancellation, captured bases, event-state cleanup, project limits, comment attachment, stable variable/Program identities, loose drafts and all eight compilable existing language fixtures. Every successful fixture also exercises the exact generated-source path, which preserves the entire project, including legacy shapes and disabled code. The B03 work below adds preservation of disabled descendants during edited conversion.

Two [browser conversion tests](../tests/e2e/bridge-converter.spec.ts) build the real converter and parser worker as test-only assets, use local CPython 3.14.2, load the resulting JSON through the app, render the blocks, run both initial and edited candidates, reload them and verify rejection/error order. The tests do not claim an editable Python UI. All 31 targeted browser checks passed, including the parser, existing language, events and pinned-module regressions. `pnpm check` passed type checking, 244 TypeScript tests, 119 native Python tests and the production build; the final unchanged-fixture additions then passed the full 252-test TypeScript suite.

## Function, event, module and identity evidence

Core verified on 2026-10-07. [Language conversion](../src/bridge/language-converter.ts) resolves each function's parameters, local assignments and `global` declarations before converting its body. It supports ordinary positional signatures, recursion, synchronous function values, non-capturing lambdas, direct awaited calls, project event emission/waits/registrations and existing pinned module calls/references. Calls through parameter or local function values keep their native runtime errors and evaluation order. Wrong await forms, handler calls, unsupported captures and late definitions/registrations produce positioned errors.

The semantic comparison now normalizes the initial region of plain function definitions while preserving import order and every startup/registration statement. Only definitions without annotations, decorators or defaults are accepted. Global declarations are normalized as compile-time scope metadata: every globally assigned name remains explicit, including declarations nested in conditionals. These rules preserve read-before-assignment, conditional `UnboundLocalError`, global rebinding and registration timing; they do not permit arbitrary definition hoisting across startup actions.

[Reconciliation](../src/bridge/reconcile.ts) reuses unchanged block identities within their Program/function owner, including lambda scope/parameter identities, and preserves positions and editing metadata. Function signatures retain IDs through parameter rename/reorder; an unambiguous function rename with a matching body, including recursive self-calls, also retains the function and block IDs. Ambiguous renames receive fresh identities. Disabled descendants become detached disabled drafts while their enabled successors remain in the program. Dormant shadow inputs survive, disabled function roots remain intact, and removed arguments on loose calls become separate drafts. The candidate API still does not install history into the live editor; atomic Apply/Undo and recoverable removed active code are B05 responsibilities.

Forty-nine [function bridge tests](../tests/unit/bridge-functions.test.ts) cover these scope, timing and identity behaviors through the actual parser/compiler and native Python execution. Existing function-value, lambda and event fixtures convert after a source edit. Edited synchronous, transitive, async and erroring module consumers retain every pinned definition and generated module file. Fixtures with infinite/overload behavior are structurally converted without executing them in those round-trip checks.

Five [browser converter checks](../tests/e2e/bridge-converter.spec.ts) cover numeric/collection/control-flow conversion, rejection/error order, recursive function and lambda edits/renames, local-scope errors, event payload isolation/order/Stop and calls into the unchanged pinned module. They use CPython 3.14.2 and load the candidates through the actual app. Module tests edit only `program.py`; the current read-only UI concatenates labelled module previews, which must become separate inspected files at B06. All five converter checks and three parser lifecycle checks passed on the final implementation. `pnpm check` passed type checking, 301 TypeScript tests, 119 native Python tests and the production build.

B03's authored sprite/kind integration is verified by the B04 evidence below. At that checkpoint, durable drafts, editor/run/export integration and the B08 audit remained open. Later integration evidence follows below.

## Durable drafts and editor evidence

Verified on 2026-10-07. [Draft serialization](../src/bridge/draft-state.ts), the [controller](../src/bridge/controller.ts) and the [atomic workspace transaction](../src/bridge/transaction.ts) implement B05. Project envelope version 2 preserves an exact current draft, accepted source checkpoint, SHA-256 base revision and explicit recovery entries; prior version-1 projects migrate without changing the block language version (19). The hash includes all authored workspace state, including loose blocks, layout, module pins and scene assets, while excluding draft metadata. Conversion checks the captured state after each asynchronous stage. Typing, cancellation, another Apply and disposal invalidate stale work.

Apply validates in isolation and installs one Blockly Undo event, with rollback on a live-load failure. Undo/Redo preserves later typing instead of overwriting it; its original base revision exposes any resulting conflict. Before applying changed source, the previous accepted text enters recovery. Starting from current blocks and discarding also preserve a recovery copy. Recovery stops at 20 entries or the project-size limit before losing anything; removal is explicit. Malformed draft metadata is rejected before live restoration.

Twenty-four [draft/controller unit tests](../tests/unit/bridge-drafts.test.ts) use the actual native parser and Blockly models. They cover exact Unicode/CRLF invalid-source reloads, version migration, positioned failures, malformed metadata, size/history limits, atomic functions/scopes Undo/Redo, typing before and after Undo, asset/module preservation, live rollback/event-state cleanup, changed block/layout/asset/module bases, changes during parsing, stale replies, superseding Apply, disposal and parser recovery.

## Execution and delivery evidence (B07)

Run and both export actions validate the active Python draft before capturing the accepted compilation. They use the same worker, library host, module pins, scene snapshot and source maps as block programs. Exact learner text stays in the saved project and Download draft; executable exports use the semantically checked generated source. A playable ZIP includes both, and edits made after its capture cannot change the archive.

Replay keeps the finished game's captured compilation. If an active draft or its authored project differs from the exact checkpoint validated for that run, Play again explains the choice: Run Python validates the edited program, while explicit discard permits the captured replay. Replay never applies new text or silently executes previous blocks under an invalid draft.

[Delivery browser tests](../tests/e2e/bridge-delivery.spec.ts) verify validated replay, blocking invalid and unapplied drafts, new Run/discard behavior, exact accepted source and assets in source/portable exports, transitive module pins, capture during later invalid typing, reopening the captured draft, independent playback on the exported local server with other network origins blocked, finite execution limits, Stop and recovery. Existing editor tests also verify that invalid drafts produce no Run or export, and errors from an older running revision leave newer text intact.

The collision investigation now has a deterministic reproduction: both positions around a catch-up frame can miss a small target even though intermediate physics positions overlap it. Motion now samples sprite/tile contact at each 1/120-second step, retaining transitions in order until delivery after the frame's update event. Native tests prove enter/separate ordering, tile entry and bounded queue behavior. This retains sampled sensing's documented limits; it is not continuous dynamic-body collision. The original platformer playthrough and converted platformer both pass after the fix.

Verification at this gate: `pnpm check` passed type checking, **670 TypeScript tests**, **122 native Python tests** and the production build. All **19 targeted browser tests** passed across delivery, creative-library conversion and physics, including standalone player launches. The complete regression and final audit remain the B08 gate.
